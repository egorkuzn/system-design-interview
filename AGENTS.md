# AGENTS.md

## О проекте

`system-design-interview` — русскоязычный практический roadmap для backend-разработчиков, которые готовятся к System Design интервью.

Репозиторий должен помогать читателю:

- понять, какие темы необходимо изучить и в каком порядке;
- освоить базовые концепции проектирования backend-систем;
- научиться обсуждать требования, ограничения и архитектурные компромиссы;
- практиковаться на задачах, похожих на реальные System Design интервью;
- оценивать свой прогресс по понятному учебному маршруту.

Репозиторий не должен превращаться в неструктурированный каталог ссылок, пересказ одной книги или набор описаний конкретных технологий.

## Целевая аудитория

Основная аудитория — backend-разработчики уровня junior+/middle и выше, которые уже знакомы с HTTP, SQL, базовыми структурами данных и принципами разработки серверных приложений.

Если материал требует дополнительных знаний, автор должен явно перечислить prerequisites и дать ссылки на подходящие вводные материалы.

## Язык и терминология

- Основной язык материалов — русский.
- При первом упоминании устоявшегося английского термина следует указать его в скобках: `пропускная способность (throughput)`.
- Не следует переводить термин, если перевод искажает смысл или почти не используется в профессиональной среде.
- В пределах одного материала термины должны использоваться последовательно.
- Формулировки должны быть точными, понятными и без искусственного усложнения.

## Принципы содержания

Каждый материал должен объяснять не только устройство решения, но и причины его выбора.

Обязательно рассматривай:

- какую проблему решает подход;
- при каких требованиях он применим;
- как он работает;
- преимущества и ограничения;
- архитектурные компромиссы (trade-offs);
- альтернативы и критерии выбора между ними;
- способы масштабирования;
- отказы, деградацию и восстановление;
- наблюдаемость и эксплуатационные последствия, когда это уместно;
- типичные ошибки кандидатов;
- вопросы, которые может задать интервьюер.

Не привязывай объяснение к одному продукту без необходимости. Сначала описывай концепцию, затем приводи PostgreSQL, Redis, Kafka и другие технологии как примеры реализации.

Не создавай универсальных рекомендаций без условий. В System Design ответ почти всегда зависит от требований и ограничений.

## Требования к источникам

- Используй несколько независимых источников для спорных или сложных утверждений.
- Предпочитай официальную документацию, инженерные блоги компаний, академические материалы и выступления инженеров, работавших над описываемыми системами.
- Учебные видео, статьи и сторонние репозитории можно использовать как отправную точку, но их утверждения необходимо перепроверять.
- Для сведений, которые могли измениться, проверяй актуальность на момент подготовки материала.
- Добавляй источники непосредственно в материал, а не только в общий список ресурсов.
- Не копируй тексты, схемы и иллюстрации без разрешения совместимой лицензии. Пересказывай своими словами и создавай собственные диаграммы.
- Не используй ссылки на пиратские копии книг и платных курсов.

## Использование AI

AI может помогать собирать источники, формировать структуру, редактировать текст, предлагать примеры и находить пробелы. AI не является источником фактов.

Материал, подготовленный с помощью AI, должен быть проверен человеком:

- факты подтверждены источниками;
- ссылки существуют и действительно подтверждают утверждения;
- примеры технически корректны;
- компромиссы и ограничения не скрыты;
- текст не воспроизводит защищённый авторским правом источник;
- материал соответствует заявленному уровню аудитории.

Не добавляй выдуманные метрики, ограничения, цитаты, инциденты или детали архитектуры реальных компаний.

## Назначение разделов

- `README.md` объясняет цель проекта, аудиторию, способ работы с репозиторием и точки входа.
- `ROADMAP.md` задаёт рекомендуемый порядок изучения тем. Он не используется для хранения персонального прогресса читателя.
- `docs/fundamentals/` содержит фундаментальные понятия и способы оценки систем.
- `docs/building-blocks/` описывает основные компоненты backend-архитектуры.
- `docs/patterns/` содержит архитектурные и распределённые паттерны.
- `docs/interview/` описывает процесс интервью, коммуникацию и общий framework решения задач.
- `docs/case-studies/` содержит полные практические разборы систем.
- `templates/` содержит обязательные структуры новых материалов.
- `resources/` содержит отобранные и аннотированные подборки источников.
- `.github/` содержит шаблоны и настройки процесса внесения изменений.

## Workflow изменения материалов

Работа над содержанием строится по схеме:

```text
GitHub Issue → исследование → материал → Pull Request → review → публикация
```

Для каждого значимого материала:

1. Создай или найди GitHub Issue с описанием ожидаемого результата.
2. Собери источники и зафиксируй границы темы.
3. Подготовь материал по подходящему шаблону.
4. Проверь ссылки, термины, факты и логическую целостность.
5. Создай Pull Request и свяжи его с Issue через `Closes #<номер>`.
6. Обнови `ROADMAP.md` или навигацию только тогда, когда материал готов к использованию.

Не закрывай Issue простым добавлением ссылок, если в нём ожидается самостоятельный учебный материал.

## Критерии готовности темы

Тема готова к review, если:

- определена цель и перечислены prerequisites;
- объяснена решаемая проблема;
- разобран принцип работы;
- указаны преимущества, ограничения и альтернативы;
- приведены практические примеры;
- добавлены вопросы для самопроверки или интервью;
- указаны проверенные источники;
- материал связан с соответствующим пунктом roadmap;
- отсутствуют неподтверждённые факты и некорректные заимствования.

## Критерии готовности case study

Практический разбор должен содержать:

1. уточнение задачи;
2. функциональные требования;
3. нефункциональные требования;
4. оценку нагрузки и объёма данных;
5. API или внешние контракты;
6. модель данных;
7. high-level design;
8. подробный разбор ключевых компонентов;
9. масштабирование и отказоустойчивость;
10. bottlenecks и trade-offs;
11. варианты развития решения;
12. вопросы интервьюера;
13. источники.

Не выдавай одну архитектуру за единственно правильную. Явно связывай решения с исходными требованиями.

## Правила изменений

- Делай изменения небольшими и тематически цельными.
- Не смешивай переработку структуры, новую тему и массовое форматирование в одном Pull Request.
- Сохраняй рабочие ссылки и относительные пути.
- При перемещении файла обновляй все ссылки на него.
- Не добавляй сгенерированные бинарные файлы без необходимости.
- Диаграммы по возможности храни в редактируемом текстовом формате.
- Не вводи новый инструмент или обязательный процесс, пока он не решает подтверждённую проблему проекта.

## Что не используется на первом этапе

OpenSpec не является частью первоначального workflow. Для текущего документального проекта достаточно GitHub Issues, шаблонов материалов, Pull Requests и этого файла.

Решение об OpenSpec можно пересмотреть, если в репозитории появится программный продукт, автоматизированные тренажёры или несколько AI-агентов, реализующих связанные функции по формальным требованиям.
