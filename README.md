# System Design Interview

Практический roadmap для backend-разработчиков, которые готовятся к System Design интервью и не хотят потеряться в бесконечном количестве книг, видео, статей и отдельных тем.

> Репозиторий находится на ранней стадии. Сейчас мы формируем структуру подготовки, определяем необходимую глубину тем и собираем проверенные материалы.

## Зачем нужен этот проект

Основная проблема подготовки к System Design интервью — не отсутствие информации. Материалов слишком много, а понятного маршрута между ними нет.

Легко потратить много времени на глубокое изучение одной технологии или концепции, но оставить без внимания другие вопросы, которые встретятся на интервью. Этот проект должен помочь удерживать баланс между широтой знаний, достаточной глубиной и практикой.

Roadmap должен отвечать на три вопроса:

1. **Что изучать?** — темы расположены в осмысленной последовательности.
2. **Насколько глубоко?** — у каждой темы будут границы и ожидаемый результат.
3. **Как проверить себя?** — вопросы для самопроверки и практические задачи показывают, можно ли двигаться дальше.

## Для кого

Проект ориентирован прежде всего на backend-разработчиков уровня junior+/middle и выше, которые уже знакомы с HTTP, SQL, базовыми структурами данных и разработкой серверных приложений.

Репозиторий также будет полезен разработчикам других направлений, которые хотят систематизировать знания о проектировании масштабируемых и отказоустойчивых систем.

## Что будет в репозитории

- последовательный план подготовки;
- фундаментальные концепции System Design;
- основные компоненты backend-систем;
- архитектурные паттерны и их trade-offs;
- framework прохождения System Design интервью;
- практические задачи и подробные разборы;
- отобранные книги, статьи, видео и инженерные блоги;
- вопросы для самопроверки и критерии завершения каждой темы.

Цель проекта — не создать энциклопедию распределённых систем и не собрать как можно больше ссылок. Каждый материал должен помогать принять архитектурное решение и объяснить его на интервью.

## Предварительный маршрут

Порядок и состав этапов ещё будут уточняться:

1. Формат System Design интервью и общий алгоритм ответа.
2. Сбор требований и оценка нагрузки.
3. Базовые свойства систем: latency, throughput, availability, reliability и consistency.
4. Сеть и взаимодействие сервисов.
5. Хранение данных, индексы, репликация и partitioning.
6. Кэширование и CDN.
7. Асинхронная обработка и очереди сообщений.
8. Масштабирование, балансировка нагрузки и отказоустойчивость.
9. Наблюдаемость, безопасность и эксплуатация.
10. Архитектурные паттерны.
11. Практические System Design задачи.
12. Пробные интервью и работа над ошибками.

Подробный учебный маршрут появится в `ROADMAP.md`. Пока его нет, открытые Issues будут использоваться для обсуждения структуры и содержания.

## Как развивается проект

Каждая значимая тема начинается с GitHub Issue и проходит следующий путь:

```text
Issue → исследование → материал → Pull Request → review → публикация
```

Issue определяет границы темы и ожидаемый результат. Pull Request добавляет самостоятельный материал, связывается с Issue через `Closes #<номер>` и проходит проверку источников и содержания.

## Как помочь

Сейчас особенно полезны:

- предложения по структуре roadmap;
- темы, которые обязательно встречаются на интервью;
- качественные бесплатные книги, статьи, курсы и видео;
- реальные вопросы с System Design интервью;
- примеры того, какой глубины понимания ожидают от кандидата;
- замечания о пробелах, неверной последовательности и лишних темах.

До появления шаблонов можно открыть обычный Issue и описать предложение своими словами. Для крупного материала сначала лучше согласовать границы темы в Issue, а уже затем готовить Pull Request.

## Принципы

- Объяснять причины решений, а не только устройство компонентов.
- Всегда обсуждать ограничения, альтернативы и trade-offs.
- Не выдавать одну архитектуру за единственно правильную.
- Отделять общие концепции от конкретных технологий.
- Проверять факты по надёжным источникам.
- Не копировать чужие тексты и схемы без разрешения.
- Не использовать AI как источник фактов.

Подробные правила подготовки материалов описаны в [AGENTS.md](AGENTS.md).

## Статус
